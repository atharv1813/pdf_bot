# RAGAS Evaluation — README

This document explains what RAGAS is, how it works, how each metric this
project uses is actually computed under the hood, and how it's all wired
into this project's `eval.py` to score the RAG pipeline defined in
`main.py`.

---

## 1. What is RAGAS?

**RAGAS** (Retrieval-Augmented Generation Assessment) is an open-source
framework for evaluating RAG pipelines. Instead of requiring a human to read
every generated answer and judge it, RAGAS uses an **LLM as a judge** to
score specific, well-defined dimensions of quality — automatically, at
scale, and repeatably.

A RAG pipeline has two moving parts that can each fail independently:

1. **Retrieval** — did the system find the right supporting information?
2. **Generation** — given what was retrieved, did the system write a good,
   grounded answer?

RAGAS's metrics are designed to separate these two concerns, so a bad score
tells you *which half* of the pipeline is at fault, not just "the answer was
wrong."

---

## 2. Core concepts

### 2.1 The sample schema

Every question you evaluate becomes a **sample** — a dictionary with (up to)
four fields:

| Field | What it is | Where it comes from |
|---|---|---|
| `user_input` | The question asked | The eval dataset (`single.json`, `multi.json`, `no_answer.json`) |
| `response` | What your system actually answered | Generated by **running your own graph** (`compiled_graph.invoke(...)`) |
| `retrieved_contexts` | The list of text chunks your retriever pulled back | Captured from your graph's state (`relevant_context` / `context`) |
| `reference` | The ground-truth "correct" answer | Only available when the dataset provides one (`single.json`/`multi.json`; **not** `no_answer.json`) |

Two of these (`user_input`, `reference`) come from your **eval data file**.
Two of these (`response`, `retrieved_contexts`) come from **actually
invoking your system** — RAGAS never scores a hypothetical; it scores what
your pipeline really produced.

### 2.2 Metrics need different combinations of these fields

Not every metric needs every field. A metric that needs `reference` simply
cannot run without one — which is exactly why `no_answer.json` (which has no
ground-truth answer) can only be scored with a subset of metrics.

### 2.3 "LLM-as-judge" — what that actually means mechanically

Every metric below (except pure embedding-similarity steps) works by
sending the judge LLM (`ragas_evaluator_llm` in this project) a carefully
constructed prompt asking it to do one narrow, structured task — extract a
list of claims, answer yes/no about a claim, generate a hypothetical
question, etc. — and then RAGAS turns the LLM's structured responses into a
number. This means:

- **Metric quality is bounded by judge quality.** A weak judge model gives
  noisy, less trustworthy scores regardless of how good your actual
  pipeline is. This is why this project uses Claude Sonnet 4.5 as the judge
  even though the pipeline itself could run on a cheaper model — the judge
  doesn't need to be cheap to run often, it needs to be *right*.
- **Scores are probabilistic, not exact.** Because an LLM is doing the
  judging, re-running the same evaluation can produce slightly different
  numbers between runs. Treat scores as informative signals for comparing
  runs/versions of your pipeline, not as ground-truth precision instruments.
- **The judge LLM is completely separate from the pipeline LLM.** RAGAS
  evaluates the *output* of your pipeline; it has no visibility into how
  your pipeline internally decided to retrieve or generate. It only ever
  sees the four sample fields above.

## 3. The four metrics, in depth

### 3.1 `Faithfulness`

**Needs:** `response`, `retrieved_contexts` — **no `reference` required**

**What it measures:** Is every factual claim in the generated answer
actually supported by (traceable back to) the retrieved context? This is
the primary **hallucination detector** in the RAGAS suite.

**How it's computed, step by step:**

1. **Claim decomposition.** The judge LLM is given the `response` and asked
   to break it down into a list of individual, atomic factual statements.
   For example, the response *"Keybullet Kin drop a key upon death, and
   jammed ones drop two keys instead"* would be decomposed into something
   like:
   - "Keybullet Kin drop a key upon death."
   - "Jammed Keybullet Kin drop two keys instead of one."

2. **Claim verification.** For each individual claim, the judge LLM is
   asked: *"Can this claim be directly inferred from the given context?"*
   — answered independently, claim by claim, against `retrieved_contexts`.

3. **Scoring.** The final score is the fraction of claims that were
   verified as supported:

   ```
   Faithfulness = (number of claims supported by context) / (total number of claims)
   ```

   A score of `1.0` means every claim in the answer is grounded. A score of
   `0.5` means half the claims made were unsupported — the model said
   something the retrieved documents never actually stated.

**Why decomposing into claims matters:** A single long answer might have
one hallucinated detail buried in an otherwise accurate paragraph. Scoring
the whole answer as one blob (e.g. "is this answer true, yes/no") would
either miss that detail or unfairly tank the whole score for one small
error. Claim-level scoring gives a proportional, more diagnostic number.

**Special note for `no_answer.json` in this project:** Since there's no
`reference` to compare against here, Faithfulness is the only metric that
still applies (it never needed `reference` in the first place). Its
interpretation flips slightly: if the system *did* generate an answer for
a genuinely unanswerable question, a **low** Faithfulness score is actually
the expected/correct outcome — it confirms the answer wasn't grounded in
anything real, which makes sense since nothing in the corpus could ground
it. A **high** Faithfulness score here would be a red flag: it would mean
the model found a way to sound grounded while answering a question the
documents don't actually address — worth checking `retrieved_contexts`
manually in that case, since it likely means an unrelated chunk was
mistakenly judged relevant upstream.

---

### 3.2 `AnswerRelevancy`

**Needs:** `response`, `user_input`, and an **embeddings model**

**What it measures:** Does the generated answer actually address the
question that was asked — as opposed to being vague, evasive, padded with
irrelevant detail, or subtly off-topic? Note this is explicitly **not**
about correctness — a confidently wrong but on-topic answer can still score
well here; that's what `Faithfulness`/`ContextRecall`/`ContextPrecision`
are for.

**How it's computed, step by step:**

1. **Reverse-question generation.** The judge LLM is given the `response`
   (not the original question) and asked to generate several plausible
   questions that this response would be a good answer to. This is done
   multiple times (RAGAS defaults to generating a handful of these
   candidate questions per sample) to average out noise from any single
   generation.

2. **Embedding comparison.** Each generated candidate question is embedded
   (using the embeddings model — `ragas_evaluator_embeddings` in this
   project) and compared via cosine similarity against the embedding of
   the *original* `user_input`.

3. **Scoring.** The final score is the average cosine similarity across all
   generated candidate questions:

   ```
   AnswerRelevancy = mean(cosine_similarity(embed(generated_question_i), embed(original_question)))
   ```

**Why this indirect "generate-questions-then-compare" approach, instead of
just asking the LLM "is this relevant, yes/no"?** A direct yes/no judgment
is coarse and easy for an LLM to rubber-stamp as "yes" even for a mediocre
answer. Reverse-engineering what question the answer *actually* answers,
then measuring how far that drifted from the real question, gives a
continuous, harder-to-game signal. If the answer talks around the topic
without addressing the specific thing asked, the LLM's reverse-generated
questions will drift away from the original question's embedding, and the
score drops accordingly.

**This is why embeddings are mandatory for this specific metric** — the
other three metrics only need the judge LLM for direct reasoning, but this
one fundamentally relies on vector similarity as its scoring mechanism.

---

### 3.3 `ContextPrecision`

**Needs:** `retrieved_contexts`, `reference`

**What it measures:** Of everything the retriever pulled back, how much of
it was actually useful/relevant for answering the question — i.e., how
*clean* is the retrieved set? This metric is about retrieval **noise**, not
retrieval **completeness** (that's `ContextRecall`, below).

**How it's computed, step by step:**

1. **Per-chunk relevance judgment.** For each chunk in `retrieved_contexts`
   (in the order they were retrieved), the judge LLM is asked whether that
   specific chunk is relevant to answering the question, using `reference`
   (the ground-truth answer) as the standard to judge against.

2. **Precision@k computation.** RAGAS computes a precision score that
   specifically **rewards relevant chunks appearing earlier** in the
   retrieved list, not just relevant chunks existing somewhere in the list.
   Conceptually, this is similar to information-retrieval's classic
   "precision at rank k" metric — for each position `k` in the ranked list,
   compute the precision of the top-`k` chunks, then average those,
   weighted toward correctly-ranked relevant chunks.

3. **Scoring.** The result is a value between 0 and 1: `1.0` means every
   retrieved chunk was relevant (and ideally the most relevant ones came
   first); a low score means a lot of what was retrieved was noise the
   generator had to sift through (or ignore) to produce the answer.

**Why ranking matters here:** Retrieving 15 chunks (as this project's
`RETRIEVAL_K = 15` does) where only 3 are truly relevant, but those 3
happen to be ranked first, is meaningfully better than the same 3-out-of-15
relevant chunks scattered at random positions — the former is easier for
downstream generation to use correctly, and `ContextPrecision` reflects
that by rewarding earlier-ranked relevance more heavily.

**Diagnostic value in this project:** A low `ContextPrecision` score
specifically implicates the **retriever's ranking/broadness** — e.g. the
`RETRIEVAL_K=15` value being too generous relative to how well the
`is_relevant_node` relevance filter is actually working, or the underlying
similarity search surfacing tangentially related chunks that a stricter
filter should have caught.

---

### 3.4 `ContextRecall`

**Needs:** `retrieved_contexts`, `reference`

**What it measures:** Of everything that *would have been needed* to fully
construct the reference answer, how much of it did retrieval actually
manage to find? This is the mirror image of `ContextPrecision` — precision
asks "how much of what I retrieved is useful," recall asks "how much of
what's useful did I actually retrieve."

**How it's computed, step by step:**

1. **Reference decomposition.** Similarly to how `Faithfulness` decomposes
   the generated `response` into individual claims, `ContextRecall`
   decomposes the **`reference`** (the ground-truth answer) into individual
   statements/facts that would need to be present to fully justify that
   answer.

2. **Per-statement attribution check.** For each of those reference
   statements, the judge LLM checks whether that specific fact **can be
   found somewhere in `retrieved_contexts`** — i.e., was the information
   needed to state this fact actually retrieved, regardless of whether the
   generated `response` ended up using it correctly.

3. **Scoring.** The final score is the fraction of reference statements
   that were traceable back to something in the retrieved context:

   ```
   ContextRecall = (number of reference statements attributable to retrieved context) / (total number of reference statements)
   ```

**Why this is the most important metric for `multi.json` in this
project:** Recall that `multi.json`'s questions typically expect answers
built from several distinct facts (e.g. a 5-item list). If the reference
answer has 5 required facts and retrieval only surfaced chunks covering 3
of them, `ContextRecall` will land around `0.6` — directly quantifying "the
retriever missed 2 of the 5 things it needed to find," independent of
whether the generation step did a good job with the 3 facts it *did* have
access to. A `single.json` question, by contrast, usually only has one
required fact, so `ContextRecall` there is closer to a binary "found it or
didn't."

### 3.5 How the four metrics complement each other — a worked comparison

| Scenario | Faithfulness | AnswerRelevancy | ContextPrecision | ContextRecall | What it tells you |
|---|---|---|---|---|---|
| Answer is accurate and complete, retrieval was clean | High | High | High | High | Pipeline working well |
| Answer sounds right but invents a detail not in the docs | **Low** | High | — | — | Generation is hallucinating despite decent retrieval |
| Answer is accurate but incomplete (missed some facts) | High | High | High | **Low** | Retrieval didn't find everything needed (common on `multi.json`) |
| Answer is accurate, but retrieval also pulled in a lot of junk | High | High | **Low** | High | Retriever is too broad/noisy (e.g. `k` too high, filter too loose) |
| Answer is vague or dodges the actual question | High | **Low** | — | — | Generation isn't engaging with what was actually asked |
| Model answers confidently on a genuinely unanswerable question | **Low** (desired here) | — | n/a (no reference) | n/a (no reference) | Correctly flags hallucination on out-of-scope questions (`no_answer.json`) |

No single metric tells the whole story — a pipeline can be simultaneously
faithful (not lying about what it retrieved) while still recalling poorly
(not retrieving enough to fully answer). Reading all four together, per
question, is what actually diagnoses *where* in the pipeline a weak score
originates.

## 4. Why this project needs its own LLM + embeddings for RAGAS

RAGAS's metrics need an LLM to do the actual judging (e.g. "does this claim
follow from this context?") and, for `AnswerRelevancy`, an embeddings model.
If you don't supply these explicitly, RAGAS silently defaults to OpenAI's
API — which fails immediately if you don't have `OPENAI_API_KEY` set
(this project uses AWS Bedrock, not OpenAI).

This project wires in its own judge model and embeddings explicitly:

```python
from langchain_aws import ChatBedrockConverse
from ragas.embeddings import LangchainEmbeddingsWrapper
from main import embeddings as hf_embeddings

ragas_evaluator_llm = ChatBedrockConverse(
    model="us.anthropic.claude-sonnet-4-5-20250929-v1:0",
    region_name="us-east-1"
)
ragas_evaluator_embeddings = LangchainEmbeddingsWrapper(hf_embeddings)
```

`ragas_evaluator_llm` is deliberately **separate** from the `llm` used
inside the RAG pipeline in `main.py` — even though both happen to point at
the same underlying model in this project. Conceptually, the pipeline's LLM
is the thing being tested; the evaluator LLM is the judge grading it. They
don't have to be the same model, and swapping the judge model independently
of the pipeline model is a normal thing to do (e.g. using a stronger model
as judge than the one being evaluated, to get more reliable grading).

The embeddings model reused here (`hf_embeddings`, a local
`HuggingFaceEmbeddings` instance) is the **same** one `main.py` uses to
embed documents into the vector DB — reused for consistency and to avoid
depending on an external embeddings API.

## 5. How this project structures its evaluation

The project has three separate eval datasets, each testing a different
failure mode:

### `single.json` — single-hop questions
Answerable from one clear fact/passage. Tests baseline retrieval +
generation correctness. Scored with all four metrics.

### `multi.json` — multi-fact questions
Despite the name, these aren't necessarily spread across multiple
*documents* — they require synthesizing **multiple separate facts**
(often scattered across several chunks of the same source document) into
one complete answer, e.g. a question expecting a 5-item list back. This
tests whether retrieval pulls back *enough* of the right chunks, and
whether generation correctly aggregates all of them rather than answering
from just the first relevant snippet found. `ContextRecall` is the most
diagnostic metric here (see §3.4) — a drop in recall specifically (more
than on `single.json`) points at retrieval failing to gather all the
necessary pieces, not a generation problem.

### `no_answer.json` — deliberately unanswerable questions
These questions have **no correct answer** in the source documents at all
— they exist to test whether the system correctly recognizes "I don't know"
rather than confidently fabricating a plausible-sounding answer.

RAGAS's standard metrics are not built for this scenario — there's no
`reference` to compare against, and RAGAS has no built-in concept of
"should the system have refused to answer." Two things are done instead:

1. **`Faithfulness` only**, as an indirect hallucination signal (see
   §3.1's special note).
2. **A custom refusal-rate check** (`check_refusal_rate` in `eval.py`) that
   directly measures, per question, whether the system found no relevant
   context (correct refusal) or found something and answered anyway (a
   candidate for manual hallucination review).

This hybrid approach — RAGAS for what it's built for, a custom check for
what it isn't — is intentional, not a workaround.

## 6. What each `EvaluationDataset` sample looks like in practice

```python
{
    "user_input": "What do keybullet kin drop?",
    "response": "Keybullet Kin drop a key upon death. However, if the player does not manage to kill them in time, they will disappear.",
    "retrieved_contexts": [
        "Keybullet Kin are enemies that drop a key upon death...",
        "If jammed, Keybullet Kin drop 2 keys instead of 1...",
    ],
    "reference": "Keybullet kin drop a key upon death."   # only present for single.json / multi.json
}
```

`document_index` (present in the source JSON files) is **never** passed
into the pipeline at inference time — it would leak information the system
would never actually have in production (a real user never tells the
system which source file to search). It's carried through separately, as
`_document_index`, purely for **post-hoc analysis** — e.g. grouping scores
by source document afterward to see if certain files are systematically
harder:

```python
df.groupby("document_index")[["faithfulness", "context_recall"]].mean()
```

## 7. Reading the output

`evaluate(...)` returns aggregate scores (one float per metric, averaged
across the whole dataset). For debugging, `.to_pandas()` gives a per-sample
breakdown — this is usually far more useful than the aggregate, since it
shows exactly *which* questions are weak and on *which* axis:

```python
df = single_scores.to_pandas()
print(df[["user_input", "faithfulness", "answer_relevancy",
          "context_precision", "context_recall"]])
```

Use the comparison table in §3.5 to interpret which combination of
low/high scores on a given row points at a retrieval problem versus a
generation problem.

## 8. Operational notes specific to this project

- **Model calls add up fast.** Each graph run makes several LLM calls
  (routing decision → per-document relevance grading → generation →
  support check → usefulness check, possibly looping through revision).
  RAGAS's own metrics make additional judge-LLM calls on top of that, per
  sample, per metric — and `Faithfulness`/`ContextRecall` specifically make
  *multiple* calls per sample internally (one for decomposition, then one
  per claim/statement for verification). Running the full eval across all
  three files can mean hundreds of LLM calls in one run — worth testing on
  a small slice (e.g. the first 3 items of each file) before running the
  full set.

- **Transient failures are handled defensively.** `run_query_for_eval` in
  `eval.py` wraps the graph invocation in a try/except, and
  `filter_failed` strips out any question that failed before it reaches
  RAGAS scoring — so a single flaky LLM call doesn't crash the whole eval
  run or corrupt the aggregate scores with crash artifacts (empty
  `response`/`retrieved_contexts`).

- **Internal bookkeeping fields are stripped before scoring.** Fields this
  project adds for its own use (`_had_relevant_context`, `_error`,
  `_document_index`) are removed via `strip_internal()` before any sample
  is handed to `EvaluationDataset.from_list(...)`, since RAGAS only expects
  its own known schema keys.

- **Scores fluctuate run-to-run.** Because every metric here relies on an
  LLM judge (and, for `AnswerRelevancy`, a stochastic multi-question
  generation step), don't treat small score differences between two runs
  of the same pipeline as meaningful — look for consistent, larger shifts
  across multiple runs before concluding a change actually helped or hurt.
